- **Why the gate is mandatory (presenter, ~09:10):** the model picks tools unreliably — sometimes it calls a tool, sometimes it doesn't — so verification is NOT an optional tool. It lives inside `submit_memo` (the only path to filing): off → filed "unverified"; on → `verify_memo` rules, then `verify_claims`; problems → refused with the problem list; MAX_REFUSALS → escalates to a human; pass → filed "awaiting_signoff" for attorney review. Abel's framing: a memo that fails the checklist should not be submittable at all — in this design it isn't; refusal is the tool's return value.
- ~09:12 PT — **Format + order (presenter):** the memo is structured JSON, never free text — the `submit_memo` tool definition itself is the format gate (JSON schema: `additionalProperties: false`; required conclusion/findings/gaps; each finding requires item/status/summary/citations; status is an enum proven/not_proven/escalated; citations are {document_id, page, quote} objects, max 3 per finding). Only because the memo arrives in that fixed shape can code check it at all. "Proven" is backed by claims: `record_fact` stores a claim + the exact quote it rests on (quote verified against the page at record time), and a proven finding must trace to those recorded claims. **Check order is fixed: deterministic first, judge second** — `verify_memo` (rules vs the case record, no model call, cheap) runs before `verify_claims` (Muse Spark judging whether each quote supports its claim). A memo that fails the rules never reaches the judge; the semantic check only spends a model call on memos that are already structurally complete and record-consistent.
- ~09:13 PT — **Why the checklist gets a layer too (presenter):** Session 1 is the proof — with verification off, `submit_memo` just filed whatever the agent produced; a bad memo *was* the answer. The checklist is the same risk one step earlier: it's the plan every later tool works against, so an item missing there (e.g. seniority in the test fixtures) is never investigated, never has facts, and the memo fails at the end — or worse, passes incomplete. So `set_checklist` carries the same mandatory pattern: the check runs inside the tool against the ground-truth reference, the agent gets directional feedback only, and after 3 refused checklists the incomplete one is accepted WITH its coverage score kept on record (never silently whole). Plan-time gate + delivery-time gate: catch the omission where it's cheapest to fix.

- ~09:15 PT — **The closed loop (presenter):** with both checks built and VERIFICATION=on, a run is now a loop, not a straight line: agent sets checklist → check runs inside the tool → problems come back as the tool result → agent revises and retries; same at submit_memo (rules, then claims). The agent never sees a "done" state the checks haven't approved. The loop is bounded on purpose: MAX_REFUSALS (3) at each gate, then the run leaves the loop and escalates to a human — an agent that could retry forever would just be a slower way to be wrong. Feedback shape differs by gate: checklist feedback is directional only (ground truth never leaks); memo feedback is the explicit problem list, because the agent wrote the memo and can fix named problems without learning anything it shouldn't.

- ~09:17 PT — **Proving a number wasn't hallucinated (presenter Q from Abel):** the chain is: number → finding's citation quote → recorded fact → verbatim text on the document page. `record_fact` refuses any quote not found on the cited page (normalized) at record time, so a made-up number can never become a fact; `verify_memo` requires every memo citation to match a recorded fact exactly, so a number can't be altered or invented at memo time; `verify_claims` judges whether numbers in the summary stay inside what the quotes say. Anything in the memo that can't be traced down that chain is unproven by construction. Known soft spot: summary prose is judged by a model, not code — a stronger deterministic upgrade is a numeric-token audit (every number in a finding's summary must appear in its citations' quotes), a candidate for the 10:30 debrief list, not part of the workshop build.

- ~09:24 PT — **Cost side of the loop (presenter):** the branched run now works the plan→act→observe loop toward `submit_memo` with a larger turn budget (40 in the console). Verification trades turns for accuracy: each refusal costs a turn, each check is a model call or a record pass, and a verified run is slower and more expensive than an unchecked one — Session 1's unchecked run was *faster* and wrong. The turn budget + refusal caps are what keep that trade bounded: accuracy improves per turn spent, but the run cannot spend forever, and the exit conditions (pass, escalate, sign-off) are all defined before the loop starts.
- ~09:29 PT — **Session synthesis (Abel's framing):** the architecture rests on two pillars — (1) **deterministic verification checks** wherever a question can be settled by code (quote-on-page, citation↔fact matching, coverage vs record, signature verdicts, open requests), with a model judge only for the irreducibly semantic residue (does the checklist cover the reference; does a quote support a claim); (2) **human in the loop** at every point the loop cannot settle itself — escalation after refusal caps, evidence release, final sign-off. Portable version for RobotForge: the gate is the deterministic pillar (measured vs ground truth, thresholds in code); Abel's own taps on deploys/merges/submissions are the human pillar. Neither pillar trusts the agent's self-report.
